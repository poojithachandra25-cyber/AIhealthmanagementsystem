Update · website chatbot

Reviewed 25 Nov 2026
layout/chatbot/* · app.html · server: routes/chat.js, chat/knowledge.js, chat/basic.js

A floating assistant on every page (Specs/chatbot.md). It answers from the hospital's own data, with Claude (claude-opus-5-5) when the server has credentials, or with a keyword-based basic mode otherwise.

  • Answers are grounded in live MySQL data (departments, services, fees with GST, doctors, consulting hours) plus a written guide to the site's flows. The prompt forbids inventing details and points visitors to Contact when unsure.
  • Only public information goes into the prompt: no patient data, bills or appointments, so the bot can't leak them.
  • Safety: no diagnosis or medicine advice, an emergency redirect, prompt-injection guidance, and server-side refusal fallbacks (fallbacks: "default").
  • The input is bounded (20 turns, 1000 characters per message) and the endpoint is rate-limited. The knowledge block is byte-stable for 5 minutes, so Claude's prompt cache gets hits.
  • If Claude is unreachable or the key is invalid, it falls back to basic mode, so the widget never dead-ends.
MediumA public AI endpoint needs stronger abuse limitsB1
Where
routes/chat.js (rateLimited)
Problem
Once an API key is set, every message costs money. The limit is per IP and held in memory, so it resets on restart, is shared by everyone behind one NAT, and doesn't cap total daily spend.
Fix
Move the limit to a shared store, such as a MySQL table, with a daily message cap. Consider requiring sign-in or a CAPTCHA for long conversations, and set a spend limit on the Anthropic account.
LowBasic mode only understands fixed keywordsB2
Where
chat/basic.js
Problem
Phrasings outside its keyword lists get the generic "I'm not sure" reply. It's meant only as a fallback.
Fix
Set ANTHROPIC_API_KEY so Claude answers, and keep basic mode for outages.
LowThe spec's MCP option isn't usedB3
Where
routes/chat.js
Problem
The Claude API's MCP connector can only reach MCP servers at a public HTTPS address. This app's data is on localhost, so the hospital facts go into the prompt instead. That is simpler and suits a dataset of this size.
Fix
Once the API is deployed publicly, expose the same lookups (doctors, slots, fees) as a remote MCP server and attach it with the mcp-client beta, so the bot can answer live slot questions.

Update · patient lab report uploads

Reviewed 25 Nov 2026
patient/report-uploads/* · core/files.ts · doctor/case-dialog (Reports tab) · server: routes/records.js, routes/doctor-cases.js, utils/uploads.js

Patients upload their own lab reports on Medical Records. Doctors with an appointment see them in View / Update → Reports.

  • The file type is checked by its content (magic bytes), not by name or the browser's claim. A text file renamed to .pdf is rejected.
  • The 5 MB limit is enforced in the browser and on the server, and only the upload route accepts large request bodies.
  • Files are served with X-Content-Type-Options: nosniff, no-store caching and a cleaned file name. Doctor access goes through their own appointment with the patient.
LowFiles are stored in the database, and nothing scans them for malwareU1
Where
patient_reports.data (LONGBLOB), utils/uploads.js
Problem
That's fine at demo scale, but database backups grow with every upload, and a PDF that passes the type check could still carry malicious content when a doctor opens it.
Fix
For production, move files to object storage (database row → storage key), scan uploads, and set a per-patient storage quota.
LowDoctors keep access to uploads after an appointment is cancelledU2
Where
routes/doctor-cases.js (/uploads/:reportId/file)
Problem
Access is scoped through the appointment, but a cancelled appointment still grants it (the same pattern as D1).
Fix
Require the appointment to be pending, confirmed or completed.

Update · new patient screens

Reviewed 22 Nov 2026

Added for the revised Specs/patientdashboard.md: each side-menu view is now its own screen (?view=mappointments, records, billing, profile), with department fees, GST billing, a dummy payment gateway, invoice and record PDFs, and an editable profile.

  • Booking and its bill are created in one transaction, so a booking can never exist without a bill.

  • One component-scoped PatientStore feeds every view, so a payment or cancellation shows up everywhere without reloading.
  • jsPDF loads on demand in its own chunk, so the initial bundle didn't grow.
  • Profile updates are validated on both sides, and changing the email checks that no other account uses it.
